# ADR 0005: Deploy to Render for a real, browsable environment

Status: accepted

Date: 2026-09-24

## Context

Everything built so far has only been run locally, inside this session's
sandbox. The user wants to actually look at the running app in a browser
themselves, not just read about verified local test runs. Needed a
hosting platform to get there.

## Decision

Deploy to **Render**, via a committed `render.yaml` Blueprint:

- One web service (Next.js, Node runtime) built with
  `npm ci && npx prisma generate && npm run build`.
- One managed Postgres database (`chatter-db`, Postgres 16).
- `preDeployCommand` runs `prisma migrate deploy` then
  `scripts/apply-sql-migrations.mjs` (new — applies `db/migrations/*.sql`
  via the `pg` driver rather than shelling out to `psql`, which isn't
  guaranteed present in Render's build image) — both confirmed
  idempotent by actually running each twice locally before trusting
  them in an automated pipeline, so this is safe on every deploy, not
  just the first.
- `AUTH_SECRET` auto-generated by Render; every other secret
  (`ANTHROPIC_API_KEY`, `GOOGLE_CLIENT_ID`/`SECRET`, `VOYAGE_API_KEY`,
  `SHOPIFY_CLIENT_ID`/`SECRET`, `APP_BASE_URL`) has no safe default and
  is filled in via the Render dashboard — none of these can be
  auto-provisioned; they need real accounts/credentials the user holds.

## Alternatives considered

- Vercel — a natural Next.js-first choice, but its Postgres story
  doesn't include pgvector as a built-in managed option the way Render's
  does; would mean a separate DB provider, more moving parts.
- Fly.io / a raw VM — more control, more to operate (no managed
  Postgres+pgvector, no Blueprint-as-code equivalent as simple as
  Render's) for a stage where "get it running and look at it" is the
  actual goal, not infrastructure ownership.

## Consequences

- This picks a hosting *platform* for now, not a final answer to
  `docs/open-questions.md` #1 (hosted SaaS vs. also self-hostable) —
  that's a product/business decision, separate from "where do we deploy
  to look at it today."
- Confirmed real, platform-specific behavior worth recording: Render
  Postgres allow-lists `pgvector` for the app's own default role — no
  separate superuser step is needed there, unlike the local setup
  documented in README.md, where `CREATE EXTENSION` required a
  superuser connection. `db/migrations/0002_pgvector.sql`'s comment
  reflects both.
- Google OAuth and Shopify's redirect URIs depend on the real Render
  URL, which only exists after the first deploy — those integrations
  need a second pass once that URL is known (update the Google Cloud
  Console OAuth app's authorized redirect URI, and `APP_BASE_URL`).
